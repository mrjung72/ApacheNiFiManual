제품정보

NiFi Toolkit는 독립 및 클러스터 된 환경에서 NiFi 설정 및 지원에 여러 명령 줄 유틸리티를 포함합니다. 유틸리티는 다음과 같습니다 :

  • CLI - 더 cli 도구는 관리자가 NiFi 및 NiFi Registry 인스턴스와 상호 작용하여 버전의 흐름 및 관리 프로세스 그룹 및 클러스터 노드와 같은 작업을 자동화 할 수 있습니다.

utilities는 스크립트에서 실행됩니다. bin NiFi Toolkit 설치 폴더.

NiFi Toolkit는 NiFi에서 별도로 다운로드됩니다. Apache NiFi 다운로드 사이트 맵

안전한 환경에서의 실행을 위한 필수품

보안 노드 및 클러스터의 경우, 두 개의 정책이 미리 구성되어야합니다.

  • 컨트롤러 액세스 – 이러한 유틸리티에 액세스 할 수있는 사용자는 NiFi에서 "액세서리 액세스"정책을 작성하여 허가해야합니다 (/controller) 둘 다 전망 및 수정 권리

  • 프록시 사용자 요청 – 이전에 설정하지 않은 경우 노드의 정체성 ( 노드의 인증서의 DN 값)은 사용자를 대신하여 프록시 요청을 승인해야합니다.

보안 환경에서 Notify 또는 Node Manager 도구를 실행할 때 proxyDN flag 옵션을 제대로 식별하려면 이러한 명령을 실행할 권한이 있는 사용자를 식별해야 한다. 비보안 환경에서 Node Manager 도구의 상태 작동을 실행하면 flag가 무시됩니다.

NiFi 클립

이 도구는 NiFi 및 NiFi Registry와 상호 작용하는 CLI를 제공하여 NIFi Registy에서 NiFi 인스턴스로의 흐름을 배포하거나 프로세스 그룹 및 클러스터 노드를 관리합니다.

부동산/건축

대부분의 명령은 NiFi 또는 NiFi Registry 인스턴스의 baseUrl을 지정해야 합니다.

예를 들어 NiFi Registry 인스턴스의 버킷을 나열하는 명령은 다음과 같습니다.

./bin/cli.sh registry list-buckets -u http://localhost:18080

모든 명령에서 URL (및 아마도 TLS에 대한 다른 옵션 인수)을 지정하는 것을 방지하려면 반복적 인 인수를 포함하는 속성 파일을 정의 할 수 있습니다.

로컬 NiFi Registry 인스턴스의 예 속성 파일은 다음과 같습니다.

 baseUrl=http://localhost:18080
 keystore=
 keystoreType=
 keystorePasswd=
 keyPasswd=
 truststore=
 truststoreType=
 truststorePasswd=
 proxiedEntity=

이 속성 파일은 지정하여 명령에 사용할 수 있습니다. -p:

./bin/cli.sh registry list-buckets -p /path/to/local-nifi-registry.properties

Dev, QA 및 Prod와 같은 상호 작용할 계획이 있는 각 환경에 대한 속성 파일을 유지할 수 있습니다.

각 명령에 속성 파일을 지정할 뿐만 아니라 속성 파일이 지정되지 않은 이벤트에서 기본 속성 파일을 설정할 수 있습니다.

기본 속성 파일은 지정됩니다. session 개념, 사용자 홈 디렉토리에 persists 호출 파일 .nifi-cli.config 설정.

NiFi의 기본 속성 파일을 설정하는 예는 다음과 같습니다.

./bin/cli.sh session set nifi.props /path/to/local-nifi.properties

NiFi Registry의 예는 다음과 같습니다.

./bin/cli.sh session set nifi.reg.props /path/to/local-nifi-registry.properties

위의 속성을 위에 작성합니다. .nifi-cli.config 설정 사용자의 홈 디렉토리에 URL 또는 속성 파일을 지정하지 않고 명령을 실행할 수 있습니다.

./bin/cli.sh registry list-buckets

위의 명령은 이제 사용할 것입니다. baseUrl 이름 * 로컬 nifi-registry.properties.

인수를 해결하는 순서는 다음과 같습니다.

  • 속성 파일 또는 세션에서 직접 인수 overrides

  • a 속성 파일 인수 (-p) 세션을 overrides

  • 다른 사람이 지정할 때 세션이 사용됩니다.

보안 설정

NiFi 및 NiFi Registry가 보안되면 CLI에서 실행된 명령은 TLS 연결을 만들고 원하는 작업을 수행 할 권한을 가진 사용자로 인증해야합니다.

현재 CLI는 클라이언트 인증서와 선택적 proxied-entity를 인증합니다. 일반적인 시나리오는 NiFi 또는 NiFi Registry가 설치되는 노드 중 하나에서 CLI를 실행할 수 있습니다. CLI는 NiFi/NiFi Registry 인스턴스와 동일한 키스토어와 truststore를 사용할 수 있습니다.

보안 구성은 이전 섹션에서 설명 된 속성 파일 중 하나에 per-command 또는 지정할 수 있습니다.

아래 예는 NiFi Registry이지만, 같은 개념은 NiFi 명령에 적용됩니다.

예 - Proxied-Entity 없이 안전한 NiFi Registry

"CN=user1, OU=NIFI"의 인증서를 포함하는 keystore를 가지고 있습니다. 예를 들어 속성 파일은 다음과 같습니다.

 baseUrl=https://localhost:18443
 keystore=/path/to/keystore.jks
 keystoreType=JKS
 keystorePasswd=changeme
 keyPasswd=changeme
 truststore=/path/to/truststore.jks
 truststoreType=JKS
 truststorePasswd=changeme

이 예에서, 명령은 "CN=user1, OU=NIFI"로 실행됩니다. 이 사용자는 NiFi Registry에서 사용자이어야하며, 연결 물통에 접근하는 명령은 이 사용자에 액세스 할 수 있습니다.

예 - Proxied-Entity를 가진 안전한 NiFi Registry

NiFi Registry 자체의 키 저장소에 액세스 할 수 있으며 NiFi Registry는 Kerberos 또는 LDAP 인증을 허용하도록 구성되어 예 속성 파일이 다음과 같습니다.

 baseUrl=https://localhost:18443
 keystore=/path/to/keystore.jks
 keystoreType=JKS
 keystorePasswd=changeme
 keyPasswd=changeme
 truststore=/path/to/truststore.jks
 truststoreType=JKS
 truststorePasswd=changeme
 proxiedEntity=user1@NIFI.COM

이 예에서 인증서 키스토어 NiFi Registry 서버의 경우, 예를 들어 "CN=localhost, OU=NIFI". 이 정체성은 NiFi Registry의 사용자로 정의되고 'Proxy'에 대한 권한을 부여해야합니다.

"CN=localhost, OU=NIFI"는 실행할 명령이 될 것입니다. 사용자1@NIFI.COM.

백링

대화형 CLI를 사용할 때, 일반적인 시나리오는 이전 결과에서 다음 명령에 입력합니다. Back-referencing은 위치 참조를 통해 이전 명령에서 결과를 참조하기위한 단축키를 제공합니다.

모든 명령은 back-references를 생성합니다. 명령이 back-referencing을 지원한다면, 사용법을 확인합니다. 
#> registry list-buckets help
Lists the buckets that the current user has access to.
PRODUCES BACK-REFERENCES

back-references를 사용하는 일반적인 시나리오는 다음과 같습니다.

  1. 사용자는 레지스트리 인스턴스에서 사용 가능한 버킷을 탐구하여 시작합니다.

    #> registry list-buckets
#   Name           Id                                     Description
-   ------------   ------------------------------------   -----------
1   My Bucket      3c7b7467-0012-4d8f-a918-6aa42b6b9d39   (empty)
2   Other Bucket   175fb557-43a2-4abb-871f-81a354f47bc2   (empty)

  2. 사용자 다음 위치 1의 이전 결과에서 양동이 ID를 사용하여 양동이 중 하나에서 흐름을 볼 수 있습니다.

    #> registry list-flows -b &1
Using a positional back-reference for 'My Bucket'
#   Name      Id                                     Description
-   -------   ------------------------------------   ----------------
1   My Flow   06acb207-d2f1-447f-85ed-9b8672fe6d30   This is my flow.

  3. 사용자는 이전 결과에서 흐름 id에 back-reference을 사용하여 흐름의 버전을 볼 수 있습니다 1

    #> registry list-flow-versions -f &1
Using a positional back-reference for 'My Flow'
Ver   Date                         Author                     Message
---   --------------------------   ------------------------   -------------------------------------
1     Tue, Jan 23 2018 09:48 EST   anonymous                  This is the first version of my flow.

  4. 사용자 배치 버전 1 흐름 사용 back-references to the Bucket and flow id from step 2

    #> nifi pg-import -b &1 -f &1 -fv 1
Using a positional back-reference for 'My Bucket'
Using a positional back-reference for 'My Flow'
9bd157d4-0161-1000-b946-c1f9b1832efd

4 단계는 단계 2에서 결과를 참조 할 수 있기 때문에 list-flow-versions 단계 3에 있는 명령은 back-references를 일으키지 않습니다, 그래서 단계 2에서 결과는 아직도 유효합니다.

명령 추가

NiFi 명령을 추가하려면 확장 된 새로운 클래스를 만듭니다. AbstractNiFiCommand:

public class MyCommand extends AbstractNiFiCommand {

  public MyCommand() {
      super("my-command");
  }

  @Override
  protected void doExecute(NiFiClient client, Properties properties)
          throws NiFiClientException, IOException, MissingOptionException, CommandException {
      // TODO implement
  }

  @Override
  public String getDescription() {
      return "This is my new command";
  }
}

새 명령을 추가 NiFiCommandGroup:

commands.add(new MyCommand());

NiFi Registry 명령을 추가하려면 동일한 단계를 수행하지만 확장 AbstractNiFiRegistryCommand, 명령을 추가 NiFiRegistryCommandGroup.

수출 모든 흐름

당신은 사용할 수 있습니다 export-all-flows 다음 작업을 수행하려면:

  • 모든 버킷 목록

  • 각 물통을 위해, 명부 모든 교류

  • 각 흐름의 경우, 모든 버전 목록

  • 각 버전을 제공된 디렉토리로 내보내기

명령을 실행하면 --outputDirectory 모수. 디렉토리는 올바르게 설정하고 권한이 있어야 합니다.

모든 흐름 가져 오기

당신은 사용할 수 있습니다 import-all-flows 다음 작업을 수행하려면:

  • 모든 파일 목록, 흐름 버전을 대표, export-all-flows에 의해 생성된 디렉토리에서

  • 모든 대응 물통 만들기

  • 모든 대응 흐름 만들기

  • 모든 해당 플로우 버전 가져 오기

명령을 실행하면 2 매개 변수가 필요합니다.

  • --input 매개변수는 파일들을 읽는 디렉토리를 나타냅니다.

  • --skipExisting 옵션 매개 변수, 기존의 흐름과 흐름 버전 생성을 처리하는 방법을 구성. Flow 및 Flow 버전 생성을 제공하면 누락된 Flow 버전에 관계없이 건너 뛸 수 있습니다. 누락된 플로우 버전이 생성되지 않는 경우.

제품 정보

import-all-flows 명령의 입력 소스는 export-all-flows 명령에 의해 생성되어야 합니다. 이동 충돌을 피하기 위해, 이 활동 중 NiFi Registry에서 수정이 수행되어야합니다. 동일한 이름과 물통과 교류는 동등합니다.

  • 모든 흐름 버전 수출:

    ./bin/cli.sh registry export-all-flows -u http://localhost:18080 --outputDirectory "/my_dir/flow_exports"

  • 모든 흐름 버전 가져 오기 :

    ./bin/cli.sh registry import-all-flows -u http://localhost:18080 --input "/my_dir/flow_exports" --skipExisting

사용 사례 2 : 데이터 복제

NiFi 1은 NiFi Registry 1과 NiFi 2에 연결됩니다.

재해 복구 목적으로 NiFi Registry 1의 데이터는 일정한 작업을 통해 NiFi Registry 2로 복제되어야 합니다.

Nifi Registry 2의 초기 버전은이 도구에 의해 생성되어야합니다.

누락된 물통, 교류 및 버전은 창조될 것입니다. 버킷과 흐름이 누락된 버전이 생성됩니다.

  1. 수출 버전:

    ./bin/cli.sh registry export-all-flows -u http://nifi-registry-1:18080 --outputDirectory "/my_dir/flow_exports"

  2. 수입 버전:

    ./bin/cli.sh registry import-all-flows -u http://nifi-registry-2:18080 --input "/my_dir/flow_exports"
