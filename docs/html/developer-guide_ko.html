제품정보

이 개발자 가이드의 의도는 Apache NiFi를 이해하는 데 필요한 정보를 가진 독자를 제공하는 것입니다. 확장은 개발 및 구성 요소 개발 뒤에 생각 프로세스를 설명하는 데 도움이됩니다. 그것은 소개를 제공합니다 확장을 개발하는 데 사용되는 API의 설명. 그것은 아니지만, 각각에 대해 큰 세부 사항으로 이동 API의 방법 중, 이 가이드는 대신 API의 JavaDocs를 보완하기위한 것입니다. 이 가이드는 독자가 Java 7 및 Apache Maven에 익숙하다고 가정합니다.

개발자가 이 가이드를 작성했습니다. 이 읽기 전에 예상된다 가이드, NiFi의 기본 이해와 dataflow의 개념이 있습니다. 그렇지 않다면, NiFi 개요 그리고 NiFi 사용자 가이드 NiFi의 개념에 익숙하게.

관련 링크

FlowFile은 데이터의 조각을 상관하는 논리적인 표기법입니다. 그 데이터에 대한 Attributes의 설정. 이러한 속성은 FlowFile의 고유 식별자뿐만 아니라 이름, 크기 및 다른 어떤 수 유량별 값. FlowFile의 내용과 속성 FlowFile 객체를 변경할 수 있습니다. 관련 기사 FlowFile에 대한 수정은 ProcessSession에서 가능합니다.

FlowFiles의 핵심 속성은 org.apache.nifi.flowfile.attributes.CoreAttributes 한국어 당신이 볼 수있는 가장 일반적인 속성 filename, path 그리고 uuid. 괄호의 문자열은 속성 안에 CoreAttributes enum 및 UI/API에 어떻게 나타나는지.

  • 파일명 (filename)filename): FlowFile의 파일명. filename은 어떤 디렉토리 구조를 포함하지 않아야 합니다.

  • 한국어 (ko)uuid): 체계에 있는 다른 FlowFiles에서 FlowFile를 구별하는 이 FlowFile에 할당된 보편적으로 유일한 Identifier.

  • 경로 (path): FlowFile의 경로는 FlowFile이 속하고 filename을 포함하지 않는 상대 디렉토리를 나타냅니다.

  • 절대 경로 (Commer Path)absolute.path): FlowFile의 절대 경로는 FlowFile이 속하고 filename을 포함하지 않는 절대 디렉토리를 나타냅니다.

  • 우선 순위 (priority): FlowFile 우선 순위를 나타내는 숫자 가치.

  • MIME 유형 (mime.type): 이 FlowFile의 MIME 유형.

  • 디스커버리 Reasondiscard.reason): FlowFile이 discarded 이유를 지정합니다.

  • 발전기 (Alternate Identifier)alternate.identifier): FlowFile의 UUID 이외의 식별자를 나타냅니다.

추가적인 Common Attributes

이 속성은 회원이 아닌 동안 CoreAttributes enum, 그들은 체계의 맞은편에 de facto 기준이고 대부분의 FlowFiles에 발견됩니다.

  • 파일 크기 (fileSize): 바이트에 있는 FlowFile 내용의 크기.

  • 등록일 (entryDate): FlowFile이 시스템에 입력된 날짜와 시간(즉, 생성되었습니다). 이 속성의 값은 1 월 1, 1970 (UTC)부터 밀리 초 수를 나타내는 숫자입니다.

  • Lineage 시작 날짜 (lineageStartDate): FlowFile이 복제, 병합, 또는 분할, 생성되는 "child" FlowFile에 있는 이 결과인 어떤 시간. 그 아이들이 복제, 병합, 또는 분할, 조상의 사슬은 내장. 이 값은 가장 오래된 조상이 시스템에 입력 한 날짜와 시간을 나타냅니다. 이 속성에 대해 생각하는 또 다른 방법은 시스템에서 FlowFile의 대기 시간을 나타냅니다. 값은 1970년 1월 1일(UTC)부터 밀리초 수를 나타내는 숫자입니다.

기록 설정 변경

일반적인 migrateConfiguration 구현은 소스 흐름을 표현으로 변환하는 커넥터는 나중에 다시 구축 할 수 있습니다 (원의 일련 된 버전의 VersionedExternalFlow 또는 파생된 윤곽), 그 후에 연결관의 자신의 윤곽에 그것을 단계:

@Override
public void migrateConfiguration(final ConnectorMigrationContext context) throws FlowUpdateException {
    final VersionedExternalFlow sourceFlow = context.getSourceFlow();
    final String serializedSourceFlow = OBJECT_MAPPER.writeValueAsString(sourceFlow);

    // Record the configuration the Connector wants on the other side of the migration. The framework merges this
    // delta onto the active configuration and then drives Connector.applyUpdate(workingContext, activeContext),
    // which is the same path used on every restart - so the managed Process Group is rebuilt the same way after
    // migration and after every subsequent restart.
    context.setProperties(MIGRATION_STATE_STEP_NAME, Map.of(MIGRATED_SOURCE_FLOW_PROPERTY_NAME, serializedSourceFlow));
}

setProperties 첨가제 : 단계별 기존 속성은 단계별지도가 무시하지 않는 값을 유지한다. replaceProperties destructive: 단계는 정확하게 공급한 재산 지도에 재시동하고, 지도에서 출석하지 않는 어떤 전 existing 재산은 제거됩니다.

연결관의 applyUpdate(workingContext, activeContext) 구현은 공급 된 합병 구성을 읽습니다. workingContext, 원하는 관리 프로세스 그룹을 다시 구축, 및 호출 getInitializationContext().updateFlow(activeContext, rebuiltFlow) 설치하기 프레임 워크가 동일하게 구동하기 때문에 applyUpdate(…​) 자주 묻는 질문 inheritConfiguration(…​), migrated 관리한 교류는 지속된 윤곽에서 각 재시작에 자동적으로 재건됩니다; 연결관은 이동을 살아남는 재시작하기 위하여 아무 여분도 할 필요가 없습니다.

기록 성분 국가

관리 프로세스 그룹이 재건 된 후, migrateState 관련 기사 StateManager 개별 관리 구성 요소의 상태:

@Override
public void migrateState(final ConnectorMigrationContext context) {
    final VersionedProcessGroup sourceGroup = context.getSourceFlow().getFlowContents();
    for (final VersionedProcessor sourceProcessor : sourceGroup.getProcessors()) {
        final VersionedComponentState sourceState = sourceProcessor.getComponentState();
        if (sourceState != null) {
            context.setComponentState(sourceProcessor.getIdentifier(), sourceState);
        }
    }
}

첫 번째 인수 setComponentState 소스 측면 버전 식별자; 프레임 워크는 일치 관리 프로세서 또는 컨트롤러 서비스에 그것을 해결하고 공급을 작성 VersionedComponentState 그 구성 요소의 살아있는 StateManager. Cluster-scope state는 모든 노드에 비정규적으로 적용된다. 노드가 선택된 각 노드에 있는 로컬-scope state는 클러스터화된 마이그레이션을 설치한다. 구성 요소 @Stateful anotation은 요청된 범위를 선언하지 않습니다.

setComponentState 유일한 단계는 원한 국가; 기구는 그 후에 씁니다 migrateState 반환. 커넥터 호출시 setComponentState 동일한 버전 식별자를 위해 한 번 이상, 마지막 통화 만 적용됩니다.

  • isMigrationSupported(…​) 흐름 상태, 매개변수 값, 또는 자산을 mutate하지 않아야 합니다.

  • migrateConfiguration 그리고 migrateState 자주 묻는 질문 모든 thrown 예외는 마이그레이션 및 롤을 다시 모든 측면 효과: 복사 된 자산은 삭제, 관리 프로세스 그룹 복원 getInitialFlow(), 각 성분의 StateManager state는 명확하고 persisted 활성 구성은 변경되지 않습니다.

  • Migration는 일단 연결관이 생성된 상태에서 수정되었습니다 한 번 거부됩니다. 이 프레임 워크는 해당 속성의 선언된 기본 값 또는 관리된 유량의 모든 프로세서 또는 컨트롤러 서비스가 구성 요소 상태에 저장되었을 때 변경된 구성 속성을 고려합니다. 이 체크는 시간에 평가됩니다. migrateConfiguration 불행하고, 다시 할 때마다 MIGRATE 허용된 행동은 평가됩니다, 그래서 사용자는 왜 마이그레이션이 사용할 수 없습니다. 이 체크는 persisted 윤곽 및 어떤 저장한 성분 국가가 튼튼한 근원에서 각 시간을 recomputed 때문에 재시작 안전입니다.

  • 마이그레이션은 프레임 워크의 관점에서 원샷입니다. 성공적인 마이그레이션은 구성을 작성하고, 일반적으로, 커넥터에 구성 요소 상태, 커넥터는 즉시 수정 된 것으로 간주되며, 연속 마이그레이션 요청은 커넥터가 discarded 될 때까지 거부되며 신선한 하나는 생성됩니다.
