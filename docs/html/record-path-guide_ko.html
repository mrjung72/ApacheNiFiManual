제품정보

Apache NiFi는 소화, 처리, 처리 할 수있는 매우 강력한 프로세서 세트를 제공합니다. routing, transforming 및 모든 형식의 데이터를 전달합니다. 이것은 NiFi 때문에 가능합니다. 프레임 워크 자체는 data-agnostic입니다. 데이터가 100 바이트 JSON 메시지인지 걱정하지 않습니다. 또는 100gigabyte 비디오. 이것은 매우 강력한 기능입니다. 그러나 많은 패턴이 있습니다. 다른 유형의 데이터를 처리하기 위해 신속하게 개발되었습니다.

NiFi에 의해 처리되는 자료의 한 종류는 기록 중심 자료입니다. 우리가 기록 중심이라고 말할 때 data, we are often (but not always) JSON, CSV 및 Avro와 같은 구조화된 데이터에 대해 이야기합니다. 기타 또한 "records" 또는 "messages,"로 표현 될 수있는 많은 다른 유형의 데이터가 있습니다. 결과적으로, 관제사 서비스의 세트는 이 다른 자료 체재를 파싱하고 대표하기를 위해 개발되었습니다 RecordReader API를 사용하여 일관된 방식으로 데이터. 이 데이터는 어떤 내용으로 작성되었습니다. 같은 처리 할 데이터 형식, 그래서 긴 기록 생성 할 수있는 RecordReader 데이터를 나타내는 객체.

RecordPath의 구조

NiFi의 기록은 (주로) 많은 분야로 구성되며, 각 필드는 실제로 기록 자체가 될 수 있습니다. 즉, 기록은 계층화, 또는 배열, 구조로 생각할 수 있습니다. 우리는 "inner Record"에 대해 이야기합니다. "외부 기록." 내부 기록의 자녀는 외부 기록의 후손입니다. 유사하게, 우리는 외부 기록을 참조 할 수 있습니다 내부 기록의 조상이기 때문에.

아이 연산자

RecordPath 언어는 외부 기록의 쉽게 참조할 수 있는 그런 방법으로 구조화되고, 또는 분야의 자녀 기록, 또는 후손 기록. 이를 달성하기 위해, 우리는 슬래시 캐릭터와 어린이의 이름을 분리 (/), 우리는 자주 묻는 질문 child 관련 기사 예를 들어, 우리는 두 개의 필드를 구성하는 기록이 있다고 가정합니다. name 그리고 details. 또한, 가정 details 이다. 기록과 2개의 분야가 있습니다: identifier 그리고 address. 더구나, 그것을 고려하자 address 포함 된 기록은 5개의 분야: number, street, city, state· zip. 예제, JSON for illustrative 목적이 다음과 같이 작성된 경우:

{
	"name": "John Doe",
	"details": {
		"identifier": 100,
		"address": {
			"number": "123",
			"street": "5th Avenue",
			"city": "New York",
			"state": "NY",
			"zip": "10020"
		}
	}
}

우리는 참고해서 좋습니다 zip RecordPath를 사용하여 필드: /details/address/zip. 이것은 우리가 사용하고 싶은 저희를 말합니다 details 주요연혁 "root" 기록. 우리는 그 때 참고를 원합니다 address 어린이 기록 및 zip 그 기록의 분야.

Descendant 운영자

명시적인 경로를 제공하여 zip 필드, 그것은 때때로 참조하는 데 유용 할 수있다 zip 알기 없는 분야 전체 경로. 그런 경우에, 우리는 사용할 수 있습니다 descendant 연산자 (//) 대신 child 연산자 (/). 같은 zip 위의 필드, 우리는 단순히 길을 사용하여이 수행 할 수 있습니다 //zip.

매우 중요한 구분이 있지만, 사이 child 연산자 및 descendant 통신수: descendant 연산자는 일치 할 수있다 많은 분야, 어디에 child 통신수는 대부분의 1개의 분야에 일치할 것입니다. 이를 이해하기 위해 다음 기록을 고려하십시오.

{
	"name": "John Doe",
	"workAddress": {
		"number": "123",
		"street": "5th Avenue",
		"city": "New York",
		"state": "NY",
		"zip": "10020"
	},
	"homeAddress": {
		"number": "456",
		"street": "116th Avenue",
		"city": "New York",
		"state": "NY",
		"zip": "11697"
	}
}

이제 RecordPath를 사용하는 경우 /workAddress/zip, 우리는 참조할 것입니다 zip "10020"의 가치를 지닌 필드. 기록Path /homeAddress/zip (주) 참고 사항 zip "11697"의 가치를 지닌 필드. 그러나, RecordPath //zip 이 분야의 둘 다 참고할 것입니다.

필터링

위 예제와 설명으로, 우리는 기록 내 특정 필드를 쉽게 참조 할 수 있습니다. 그러나 실제 시나리오에서 데이터는 거의 위의 예에서 간단한. 종종 우리는 우리가 언급 한 필드를 필터링하거나 정제해야합니다. 우리가 할 수 있을 때의 예는 우리는 배열 분야를 참조하고 배열에 있는 성분의 일부를 참조하고 싶을 때; 우리는 지도 분야를 참조하고 1개 또는 몇몇을 참조하고 싶을 때 Map의 특정 항목; 또는 일부 표준을 준수하면 레코드를 참조하려는 경우. 우리는 우리의 기준을 제공해서 이것을 성취해서 좋습니다 평방 브래킷 내의 RecordPath (사용 [ 그리고 ] 문자). 우리는 아래에 이러한 경우의 각각에 갈 것입니다.

기록에서 필드를 검색 할뿐만 아니라, 위에서 설명 한대로 필터링 단면도, 우리는 때때로 우리가 선정하고 싶은 분야를 정제해야 합니다. 또는 우리는 필드의 수정 된 버전을 반환 할 수 있습니다. 이렇게하려면 함수에 의존합니다. 함수의 구문은 <function name>입니다. <열려있는 모체> <args> <닫은 parenthesis>, <args>는 commas에 의해 분리된 하나 이상의 인수를 나타냅니다. 인수는 문자열 리터럴 (예 : 'hello') 또는 수 리터럴 (예 : 48), 또는 일 수 있었습니다 상대 또는 절대 RecordPath (와 같은 ./name or /id). 또한 필터 내에서 기능을 사용할 수 있습니다. 예를 들어, 우리는 같은 RecordPath를 사용할 수 있습니다. /person[ isEmpty('name') ]/id 관련 기사 id 이름이 비어있는 사람의 필드. 사용 가능한 기능 목록 및 해당 문서 아래에서 찾을 수 있습니다. 제품정보 이름 *

기타 제품

우리는 배열 필드를 참조 할 때, 필드의 값은 여러 요소를 포함하는 배열이 될 수 있지만, 우리는 그 요소의 몇 가지를 원할 수 있습니다. 예를 들어, 우리는 첫 번째 요소 만 참조 할 수 있습니다; 마지막 요소 만; 또는 아마도 첫 번째, 두 번째, 세 번째 및 마지막 요소. 우리는 단순히 특정 요소를 참조 할 수 있습니다. 사각형 브래킷 내 요소의 인덱스를 사용하여 ( 인덱스는 0 기반). 따라서 위의 기록의 수정 된 버전을 고려하십시오.

{
	"name": "John Doe",
	"addresses": [
		"work": {
			"number": "123",
			"street": "5th Avenue",
			"city": "New York",
			"state": "NY",
			"zip": "10020"
		},
		"home": {
			"number": "456",
			"street": "116th Avenue",
			"city": "New York",
			"state": "NY",
			"zip": "11697"
		}
	]

우리는 지금 첫번째 성분을 안으로 참조해서 좋습니다 addresses RecordPath를 사용하여 배열 /addresses[0]. 우리는 RecordPath를 사용하여 두 번째 요소에 액세스 할 수 있습니다. /addresses[1]· 몇 가지 요소가 배열에 존재하는지 알 수 없습니다. 그래서 우리는 배열의 끝에 백워드를 계산하기 위해 부정적인 인덱스를 사용할 수 있습니다. 예를 들어, 우리는 마지막 성분에 접근해서 좋습니다 /addresses[-1] 또는 다음 마지막 요소로 /addresses[-2]. 몇몇 성분을 참조하고 싶은 경우에, 우리는 comma 격리한 명부를 사용할 수 있습니다 성분과 같은 /addresses[0, 1, 2, 3]. 또는, 0 8를 통해 접근 성분에, 우리는 사용할 수 있습니다 range 연산자 (..), 안으로 /addresses[0..8]. 우리는 또한 이, 및 참고를 섞어서 좋습니다 syntax를 사용하여 모든 요소 /addresses[0..-1] 또는 심지어 /addresses[0, 1, 4, 6..-1]. 물론, 여기에 언급 된 인덱스의 모든 것은 위의 기록에 일치합니다, 때문에 이름 * addresses 배열은 단지 2개의 성분이 있습니다. 일치하지 않는 인덱스는 단순히 건너 뛸 것입니다.

어레이 필드와 마찬가지로 Map 필드는 실제로 여러 가지 값으로 구성됩니다. RecordPath는 열쇠를 기반으로 한 값 세트를 선택할 수있는 능력을 제공합니다. 우리는 정연한 부류 안에 인용한 끈을 이용하여 이것을 합니다. 예를 들어, 위에서의 원본 레코드를 다시 볼 수 있습니다.

{
	"name": "John Doe",
	"details": {
		"identifier": 100,
		"address": {
			"number": "123",

			"city": "New York",
			"state": "NY",

이제는 기록과 관련된 Schema가 그 것을 고려할 수 있습니다. address 필드는 기록이 아니라 오히려 Map 이름 * 이 경우, 우리가 참조하려고하면 zip RecordPath 사용 /details/address/zip RecordPath는 일치하지 않습니다. address 필드는 기록이 없습니다. 그리고 따라서 지명된 모든 어린이 기록이 없습니다 zip. 대신 타입 문자열의 키와 값이 있는 맵 필드입니다. 불행히도, JSON을 찾고 있다면, JSON이 실제로 Type 시스템을 가지고 있기 때문에 조금 혼란스러울 수 있습니다. JSON을 순서대로 변환할 때 데이터에서 작동하지만,이 구별은 중요합니다.

위의 경우, 우리는 여전히 액세스 할 수 있습니다 zip RecordPath를 사용하여 필드. 우리는 이제 약간 다른 구문을 사용해야합니다. /details/address['zip']. 이 우리가 접근하고 싶은 RecordPath를 말합니다. details 가장 높은 수준의 필드. 우리는 그에 접근하고 싶습니다. address 이름 * 이름 * address 분야는 Map 우리는 우리가 Map Key를 지정하고 싶은 것을 나타내기 위하여 정연한 부류를 사용할 수 있고, 그 때 인용에 열쇠를 지정할 수 있습니다.

더구나, 우리는 comma-separated 명부를 사용하여 1개의 지도 열쇠 보다는 더 많은 것을 선정해서 좋습니다: /details/address['city', 'state', 'zip']. 우리는 또한 우리가 원하는 경우에 모든 분야를 선정해서 좋습니다, Wildcard 연산자를 사용하여 (*): /details/address[*]. 맵 필드는 어떤 종류의 주문이 포함되지 않습니다, 그래서 숫자 인덱스에 의해 키를 참조 할 수 없습니다.

지금까지 필터의 두 가지 종류에 대해 논의했습니다. 그들 각각은 많은 가치를 허용하는 분야에서 하나 이상의 요소를 선택할 수 있습니다. 종종 시간이지만, 녹음 필드가 선택되는 제한 할 수있는 필터를 적용해야합니다. 예를 들어, 우리가 선택한 경우 zip 필드하지만 한국어 address 국가가 뉴욕이 아닌 필드? 위의 예제는 우리에게 이것을 할 수있는 방법을 제공하지 않습니다.

RecordPath는 사용자가 Predicate를 지정할 수있는 능력을 제공합니다. Predicate는 단순히 여부를 결정하기 위해 필드에 적용 할 수있는 필터입니다. 필드는 결과에 포함해야합니다. 다른 필터와 같이, Predicate는 정연한 부류 안에 지정됩니다. Predicate의 문법은 <Relative RecordPath> <Operator> <Expression>· Relative RecordPath 다른 모든 RecordPath와 마찬가지로 작동하지만 시작해야 . (현재 필드 참조) 또는 .. (현재 필드의 부모를 참조) 대신 슬래시와 참조 Predicate가 적용된 필드에 관계되는 필드. 더 보기 Operator 다음 중 하나가 있어야 합니다:

  • 본부 (=)

  • 없음 (!=)

  • 더 큰 (>)

  • 더 중대한 또는 동등한 것 (>=)

  • 보다 적게 (<)

  • 또는 동등한 것 보다는 더 적은 (<=)

더 보기 Expression 리터 값이 될 수 있습니다. 50 or Hello 또는 다른 RecordPath가 될 수 있습니다.
